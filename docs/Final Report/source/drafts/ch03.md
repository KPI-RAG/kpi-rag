## 3. Methodology

### 3.1 Overall approach and how the work was organised

KPI-RAG is a three-layer pipeline. Layer 1 turns each KPI window into a feature vector at native scale. Layer 2 is a cascade of two CatBoost models, a binary detector (Model 1) and an 11-class fault classifier (Model 2), with SHAP (SHapley Additive exPlanations) attributions for every alarm; windows labelled Normal stop here. Layer 3 retrieves comparable past incidents, adds the predicted fault's row of the alignment table (matrix v1.2) and a per-window evidence block, asks a large language model (LLM) for a structured explanation and checks the cited standard automatically. A Streamlit dashboard presents the result. {fig:arch} in Chapter 4 shows the final architecture and where each evaluation track attaches.

The work followed a cycle of building, measuring and correcting. The first prototype, described in the Phase 1 report of 12 September 2026, implemented every layer and a first evaluation of each. Before reporting its final results, the team replaced the prototype's window-level split with a split by recording session and rebuilt its zero-filled protocol columns. The first prototype's audit of the explanation layer then fixed three more defects: a citation validator that accepted any fault's standard, the wrong document type in the Doppler Shift row, and per-window evidence records that reached the dashboard but not the prompt.

The ML team's audit of the first prototype later found defects in the feature parser, the detector and the model-selection procedure. A separate audit of the ablation runs found that runs of the citation ablation had sampled windows by predicted label. Between September and October 2026 the team rebuilt each layer where its measurements showed a problem, which produced the final system (October 2026). The ML team froze one experimental protocol before any new model experiment (Section 3.4), and the citation ablation (Track C) was redesigned to sample and score against ground truth.

Raneem Alnaghy reconstructed the recording sessions and built the session split and the reject option. Farida El Ghabary developed the synthetic training data (v3) and the Model 2 recipe, and the ML team (Farida El Ghabary, Raneem Alnaghy) carried out the later model development steps 01 to 12. Rodina Khallaf produced version 1.2 of the alignment table and ran Tracks B and D. Ahmed Al Shobaki built the retrieval pipeline, the LLM explanation layer and its citation validation, the Track C evaluation and evaluation tooling, the dashboard, the test suite and the deployment.

### 3.2 Dataset: TelecomTS and exploratory analysis

TelecomTS [@feng2025telecomts; @feng2026telecomtshf] provides 32,000 labelled windows from a real 5G laboratory network ({tab:dataset}). Each window holds 128 samples at 100 ms for 16 numerical KPIs and two categorical protocol fields; the models and SHAP use the 16 KPIs. The 1,235 anomalous windows cover the 11 fault types described in Section 2.2: 10 injected into normal recordings and one real over-the-air jamming event. These 10 are called injected faults, to keep them apart from the synthetic training windows (v3) that the project generated (Section 3.7). {tab:classes} gives the short class names used throughout.

**Class imbalance.** Anomalous windows per fault type range from 279 (Jamming) to 48 (Congestion-Sudden), a 5.8-fold spread ({fig:classbal}). The detector is therefore trained on a rebalanced set and tuned for recall, since a missed fault costs more than a false alarm. Model 2 is judged by cross-validated macro-F1, because a single split leaves very few test windows for the smallest classes.

![TelecomTS holds 30,765 Normal against 1,235 anomalous windows (left), and the anomalous windows per fault type range from 279 for Jamming down to 48 for Congestion-Sudden (right).](figures/fig_class_balance.png){#fig:classbal}

**Channel discriminability.** Per-channel means of normal and anomalous windows differ most for Estimated_UL_Buffer (+1,001 %), PRB_Utilization_UL (+272 %) and UL_NumberOfPackets (+265 %), and by only 4.8 % for RSRP. Per-channel statistics therefore carry real signal, while RSRP alone is a weak fault indicator. The dataset's affected-KPI metadata cannot be used as attribution ground truth, because it is populated only for Jamming ({fig:heatmap}); the KPI effects of the injected faults must be inferred from SHAP (Section 3.8).

![The affected-KPI metadata of TelecomTS is populated only for Jamming; its darkest cells are RX_Bytes and TX_Bytes, followed by DL_BLER, UL_BLER and UL_MCS.](figures/fig_fault_kpi_heatmap.png){#fig:heatmap}

**Context-label shortcuts.** The labels column holds operational context (zone, application, mobility, congestion). Windows labelled Mobility=Yes (927) and Congestion=Yes (2,781) contain no anomaly, so a classifier could learn that Mobility=Yes means Normal, and some fields derive from the anomaly labels. The labels column is therefore excluded from model inputs, and all statistics are recomputed from raw KPI values.

### 3.3 Data split: from window level to session level

**Window-level split.** The first prototype initially split individual windows, stratified by class (a window-level split). A near-duplicate analysis then found that 31.8 % of test windows had a training window with cosine similarity of 0.999 or more, a direct result of the 75 % window overlap. A first recording-level split was rejected because all anomalous windows fell in a subset of sessions and its test set received none.

**Session-level split.** The first prototype therefore moved to a session-level holdout with test sessions chosen so that every fault type appears in both partitions, which the final system keeps. Raneem Alnaghy recovered the sessions from the timestamps with nine gap thresholds between 1 s and 24 h; the count stabilises at 300 s (33 sessions of about 970 windows, against 32 at 3,600 s). This reconstruction of the 33 sessions underlies every final result. Whole sessions go to one partition, and the test sessions are {1, 3, 4, 13, 17}. Training has 28 sessions (25,688 windows, 935 faults) and test 5 sessions (6,312 windows, 300 faults, about 4.75 %). The retrieval index uses the same partition and holds training windows only. The Phase 1 report also gave a residual near-duplicate rate for this split, which the ML team's audit could not reproduce; the final results rely instead on the fact that no session appears in both partitions.

**What the sessions contain.** Under this reconstruction, 13 of the 33 sessions contain anomalies. A later analysis by the ML team (step 04) found that of the 28 training sessions, 18 are Normal-only, 9 are fault-only and only session 0 mixes both (3,007 Normal and 93 real Jamming windows). Every session with injected faults consists entirely of faults. The training faults therefore come from 10 sessions, two with Jamming. A held-out session is thus always an extrapolation to an unseen recording, and the number of fault sessions, not of fault windows, limits how precisely models can be compared.

### 3.4 Experimental protocol for the models

The first prototype tuned both models with StratifiedGroupKFold by session and reported Model 2 mainly by five-fold session-aware cross-validation. The ML team's audit found that its feature configuration had been chosen on the test set, and that the follow-up investigations reported with the feature ablation came from notebooks never executed in their submitted state.

Before any new experiment, the ML team therefore froze one protocol (step 01) for every later decision ({tab:protocol}), with selection on the 28 training sessions only and the Nadeau-Bengio corrected paired t-test [@nadeau2003inference] for comparisons. A gain counts as material if it reaches 0.03 macro-F1 or improves the cascade materially, and the held-out sessions are evaluated once per step as a post-hoc check, never for selection. Step 01 reproduced the real-only Model 2 baseline under this protocol (macro-F1 0.2908 ± 0.0902, rounded to 0.291), and all later gains are measured against it. The Phase 1 report's five-fold estimate (0.333 ± 0.076) came from a different protocol and is not used as a reference. As a last step, session-level bootstrap intervals and a power analysis quantified the uncertainty left by 10 fault sessions.

Table: Only the final protocol selects on the training sessions alone and has a comparison test and an adoption rule; the first prototype's protocol had none of these. {#tab:protocol}

| Aspect | First prototype | Final system |
|---|---|---|
| Split | window-level stratified, then session-level holdout | session-level holdout, 33 sessions, 300 s gap |
| Data used for selection | feature configuration chosen on the test set (ML team's audit finding) | 28 training sessions only |
| Cross-validation | 5-fold, session-aware | StratifiedGroupKFold by session, 5 folds × 5 seeds |
| Comparison test | — | Nadeau-Bengio corrected paired t-test; Wilcoxon as a check |
| Adoption rule | — | p < 0.05, material gain, gain holds on the held-out sessions |
| Uncertainty | 95 % confidence interval (CI) on cross-validated macro-F1 | session-level bootstrap CIs and power analysis |

### 3.5 Feature engineering

**Scale-preserving principle.** No normalisation is applied at any stage, because normalising the raw series before extraction removes the absolute KPI level, which is itself diagnostic (Section 2.1). RQ1 tests this principle against normalised-feature and statistics-only baselines, and RQ3 asks which configuration gives the best trade-off between performance and cost.

**The first prototype's feature vector.** The first prototype computed four blocks per window ({tab:features}), 582 dimensions at the time of its ablation and 584 after the protocol block was rebuilt. The patchwise statistics keep absolute magnitude within each of 8 patches, following NuTime [@lin2024nutime], and the difference statistics capture the rate of change. Its ablation compared Config A (statistics only, 64 dimensions), Config B (statistics and patchwise scale, 320) and Config C (the full vector); its algorithm comparison also used 64 features chosen from the full vector by SelectKBest. These are the first prototype's definitions; the ML team's report uses the same names for the final models without restating them.

Table: The first prototype's vector has four feature blocks (584 dimensions after the protocol fix); the final Model 1 keeps its 64 statistics, and the final Model 2 uses 496 features. {#tab:features}

| Block or set | Dimensions | Content |
|---|---|---|
| Global statistics (Config A) | 64 (4 × 16) | mean, standard deviation, minimum and maximum per KPI, recomputed from raw values |
| Patchwise scale statistics | 256 (8 × 16 × 2) | mean and standard deviation per KPI in each of 8 equal patches |
| First-order differences | 256 (8 × 16 × 2) | mean and standard deviation of the difference signal per KPI and patch |
| Protocol encoding | 8 (4 × 2) | one-hot uplink (UL) and downlink (DL) protocol: TCP, UDP, None, EMPTY |
| Full vector after the protocol fix (Config C had 582 in the ablation) | 584 | all four blocks |
| Final Model 1 | 64 | Config A statistics, corrected parser |
| Final Model 2 | 496 | Config B + fast Fourier transform (FFT) + G1 G2 G3 (trend features), as named by the ML team; first prototype's parser |

**Status of the ablation.** On the window-level split with a Random Forest, Config A outperformed the larger configurations on both tasks, which the Phase 1 report attributed to too few training samples per feature for the larger vectors (Section 5.1). CatBoost with Config A then became the configuration of both first-prototype models. The leaky split and the ML team's audit findings weaken this evidence. Under the frozen protocol the ML team kept Config A for Model 1 and tested feature additions for each model separately (Sections 5.2 and 5.3), but did not repeat the three-configuration ablation.

**Defects and final feature sets.** The first prototype rebuilt its zero-filled protocol columns as eight one-hot columns after the ablation (582 to 584 dimensions). The ML team's audit found that the parser read "1.e-05" as 1 and −5, giving impossible block error rate (BLER) values in 492 training windows (1.9 %). Model 1 uses the corrected parser. Model 2 keeps the first prototype's parser, as the synthetic-data cache does; fixing the parser inside the generator gave a cross-validated macro-F1 of 0.385, a change the ML team judged negligible (Section 5.3, {tab:synth}). Model 2's 496 features are Farida El Ghabary's recipe (Config B and FFT features) with the trend and co-movement features (the ML team's groups G1 to G3, called trend features below) added for the final system (Section 3.7). Co-movement features undefined for a flat KPI are stored as missing values.

### 3.6 Detection and classification models

**Why a two-stage cascade.** The first prototype evaluated a single 12-class classifier (Normal and the 11 faults) and rejected it for three reasons. First, the imbalance between Normal (30,765 windows) and the rarest fault (48) made joint training unstable. Second, detection and classification need different objectives (recall for detection, macro-F1 for classification) that one model cannot tune separately. Third, a detection threshold inside a joint model cannot be moved without retraining it.

**First algorithm search.** The first prototype compared LightGBM [@ke2017lightgbm], Random Forest [@breiman2001rf], XGBoost [@chen2016xgboost] and CatBoost [@prokhorenkova2018catboost] across the four feature configurations with a five-seed robustness check and selected CatBoost, with an Isolation Forest [@liu2008iforest] as the unsupervised detection baseline. Model 1 used an 80/20 Normal/anomalous rebalance with an F2 objective, which weights recall above precision. Because the ML team's audit questioned the selection procedure, Section 5.1 gives only the resulting ranking, without the scores.

**Model 1 in the final system.** The ML team's audit found that the first prototype's Model 1 corrected the imbalance twice, by the rebalance and by balanced class weights, so it raised too many alarms. This defect and the parser defect were tested in a 2 × 2 design (step 03), and the adopted detector fixes both: 64 Config A features from correctly parsed signals, the 80/20 rebalance and no class weights, trained on 4,675 rows. Its threshold stays at 0.5, because the per-fold optimum ranged from 0.008 to 0.927 (step 02), so no tuned threshold would transfer to a new session. Targeted alternatives (step 10a), from level-jitter augmentation to shape-based detectors, did not meet the adoption rule (Section 5.2).

**Model 2 in the final system.** Nine algorithms were compared on real data only (step 07), from tree ensembles such as ExtraTrees [@geurts2006extratrees] and CatBoost on catch22 features [@lubba2019catch22] to the time-series classifiers QUANT [@dempster2024quant], MiniRocket [@dempster2021minirocket] and Hydra [@dempster2023hydra] (Section 5.1). With synthetic data added (step 08), LightGBM scored above Farida El Ghabary's CatBoost recipe but not significantly (p = 0.37), so the algorithm was not switched. The final candidates, including soft votes of CatBoost and QUANT, were also measured on the held-out sessions (step 09c, Section 5.3). The final Model 2 is CatBoost trained on 935 real and 4,250 synthetic (v3) windows (5,185 rows).

**Reject option.** The first prototype revealed an implicit catch-all class: Model 2 cannot answer "none of the above", and 82.2 % of the detector's false alarms were labelled CCI-Mild. Raneem Alnaghy's reject option, an extra Normal class for Model 2, was tested against a random Normal class and a probability threshold (steps 10 and 10c). Section 5.4 gives its design and results; the final pipeline has no reject class.

**Confidence.** The Layer 2 confidence is uncalibrated: an isotonic calibration [@zadrozny2002isotonic] was tested and removed because it erased the ranking of Model 1's scores (Section 5.4).

### 3.7 Synthetic data augmentation

In the first prototype, SMOTE (synthetic minority over-sampling technique) [@chawla2002smote] gave Model 2 a single-split gain that cross-validation did not confirm. Farida El Ghabary's v3 generator, developed afterwards, builds synthetic fault windows by copying fault effects from the real fault sessions onto Normal-session backgrounds. The generator's first evaluation, by its author, found its gain consistent but not significant, so the ML team audited the generator code (`src/v3.py`) before relying on it. Donors and hosts come only from the 28 training sessions, and generation is nested inside cross-validation: effects, references, bounds and hosts are rebuilt from each fold's training sessions, and validation uses real windows only. The generator fixes its seeds, enforces physical limits and real-data bounds, and applies a Wilcoxon test (α = 0.001) as a statistical gate. A 25-fold cache (step 09z) reproduces inline generation exactly (maximum difference 0.0), and the v3 recipe's final model was reproduced in 25 of 25 folds (0.3743).

Under the frozen protocol the ML team then compared v3 with real-only training (step 06) and tested further changes, from excluding Congestion-Gradual and Buffer Overflow from augmentation to adding the trend features. Section 5.3 gives the results ({tab:synth}) and the three limits the ML team recorded, among them that every synthetic fault copies effects from the same 10 fault sessions.

### 3.8 SHAP attribution

SHAP [@lundberg2017shap] assigns each feature an additive contribution to one prediction. The first prototype applied SHAP TreeExplainer to both CatBoost models; in the final system the three strongest SHAP attributions per alarm feed the explanation layer and the dashboard. Because the injected faults have no affected-KPI ground truth, the first prototype compared Model 2's SHAP ranking with the KPI effects expected from the specifications. Section 4.3 describes how the final export chooses the SHAP source and which features it keeps out of the top three. Each entry stores the magnitude |SHAP|, its effect on the predicted class (towards or away from it) and the KPI's direction against its normal mean (`feature_vs_normal`). The first prompts printed the magnitude as "SHAP=+x", presenting every feature as support. Yet 97 of the 1,146 top-three entries push away from the predicted class, so the prompts now state all three in words.

### 3.9 Standards alignment method

The alignment table maps each fault class to the 3GPP specification that governs it and to the O-RAN component [@oran2022arch] to act on. The predicted fault's row goes into the deployed prompt, and its references are what the citation validator accepts.

**First construction.** A go/no-go check required evidence in the GSMA knowledge graphs for at least 7 of the 10 injected fault types. Each row was built in three stages. Keyword search of the telecom-kg-rel19 graph [@yang2026kgrel19] gave a candidate 3GPP clause, and keyword search of the O-RAN specification graph [@gsma2026orankg] (15,103 nodes and 5,954 chunk nodes in the extracted evidence set) gave a candidate O-RAN component. Both were then verified against the primary specification text, recording document identifier, release, clause and evidence span. Separating direct from mechanism-level support raised coverage to 10 of 10 (6 direct, 4 mechanism-level). Jamming, a physical radio-frequency attack, was given no standard. Verification and the first prototype's audit also corrected the Doppler Shift row from TS 38.901 to TR 38.901 [@tr38901], a Technical Report. A live Neo4j/Cypher query path was set aside, because a static, validated table keeps the evidence auditable and lets Track C isolate the table's effect.

**Version 1.2.** Rodina Khallaf's revision, the "3GPP and O-RAN alignment matrix, v1.2", maps the classes to 3GPP Release 19 and records for each its domain, onset profile, causal mechanism and affected KPIs. Its author marks Jamming "Dataset Validated": a real over-the-air condition, evaluated against operational ticket logs, with no 3GPP clause or O-RAN target. The one change of primary specification moves Faulty Handover from TS 38.133 §4.3.5 [@ts38133] to TS 38.331 §5.5.4.4 and §5.5.4.1 [@ts38331]. Section 4.4 gives the final table (11 rows, 10 with a 3GPP reference) in {tab:alignment}.

### 3.10 Retrieval and explanation generation

The explanation layer (Ahmed Al Shobaki) works in four steps. It indexes the KPI narratives of past incidents offline and retrieves similar incidents of the predicted fault type for each alarm. It then prompts the LLM with the alarm's evidence, the incidents and the fault's alignment row, and normalises and validates the cited standard. Section 4.5 describes the implementation.

**Retrieval design.** The first prototype indexed the tickets and question-and-answer traces of the 935 anomalous training windows and put the predicted label in the query. A later measurement of the corpus showed that the ticket takes only 11 distinct values across these windows, one template per class. The root-cause answer in every question-and-answer trace is the class name, so ticket retrieval returned the label in another form. The final index therefore holds each training window's KPI narrative, the only window-specific text, embedded with all-MiniLM-L6-v2, a Sentence-BERT model with 384-dimensional embeddings [@reimers2019sbert; @wang2020minilm]. The vectors sit in a cosine-space ChromaDB collection [@chroma] with the fault type as metadata; an early index had used L2 distance while computing similarity as one minus the distance. Narratives exceed the model's 256-token input, and truncation was kept because averaging the embeddings of all paragraphs retrieved far worse (Section 5.6). The query is built from the alarm alone (top SHAP channels, their direction against the normal mean, uplink and downlink KPI means). A metadata filter restricts results to the predicted fault type, because text evidence alone identifies the true class only modestly above the majority-class share (Section 5.6). The top three of five retrieved incidents reach the LLM, and a top similarity below 0.35 raises a low-confidence flag, as in the first prototype.

**Prompt conditions.** The three conditions differ only in the context they add ({tab:conditions}). The header gives the predicted fault, the confidence and one line per SHAP feature, such as "RSRP: below normal (|SHAP|=0.42, toward predicted class)". One instruction block, identical in all conditions, asks for five JavaScript Object Notation (JSON) fields (root cause, 3GPP reference, O-RAN component, recommended action, reasoning trace) and gives no example standard number, since an example would hint at the answer. An earlier version had given only C3 a "use TR …, e.g. TR 38.901" hint.

Table: In the Track C prompts, C2 adds retrieved incidents to C1, and C3, the deployed configuration, also adds the evidence block and the alignment row. For Jamming, which has no 3GPP reference, the standards block states that no 3GPP clause applies. {#tab:conditions}

| Block | C1 | C2 | C3 (deployed) |
|---|---|---|---|
| Header: fault, confidence, SHAP lines | yes | yes | yes |
| Per-window evidence block | no | no | yes |
| Three retrieved incidents (KPI narratives) | no | yes | yes |
| Alignment row: standard, clause, O-RAN component | no | no | yes |
| Shared instruction block (five JSON fields) | yes | yes | yes |

**Per-window evidence block.** C3 adds a short block built from the alarm's root-cause analysis (RCA) evidence record (289 records, one per non-Jamming alarm): SHAP features, observed KPI means and the start of the causal mechanism. The first prototype's audit had found these records reaching the dashboard but not the prompt, and wired them into C3. The record's standards text is left out, because some records still carry the older Handover standard (TS 38.133) and the alignment table must be the only source of standards in the prompt. The record's "evidence status" is left out as well, because it was derived from labelled windows that include the test split. Before the final Track C run the team revised the records to match the Layer 2 SHAP top three; the revision changed the C3 evidence block of 61 of the 289 records.

**Generation and validation.** The deployed backend is Gemini 3.5 Flash Lite [@gemini] at temperature 0.1 with JSON output; the first prototype was developed with Llama 3.1 8B through Ollama. The validator accepts the first citation in the reply, normalised to a TS/TR number, only if it is among the valid references of the alarm's fault, a lookup the first prototype's audit made fault-specific. Jamming, the only fault type without a 3GPP reference, can never have a valid citation (an earlier version accepted any fault's primary standard). A template answer, the fallback produced after failed LLM calls, is always invalid, and clause numbers are not validated.

### 3.11 Evaluation design

The first prototype planned Track A for detection, Track B for explanation quality (with citation faithfulness and a TeleQnA probe) and Track C for an end-to-end ablation of the explanation layer. In the final design Track B is an LLM-judge evaluation of explanation quality (G-Eval), Track C the citation ablation, and the TeleQnA probe became Track D. {tab:tracks} gives each track's question, sample and metrics.

**Track A: detection and classification.** The detector is evaluated on the five held-out sessions at the natural rate, against the first prototype's detector. The Phase 1 report's headline detector F1 had been computed on a rebalanced subset of 1,000 windows, which the final evaluation does not repeat. Model 2 gains are measured against the real-only baseline (0.291), and a family-level accuracy treats Congestion-Gradual, Buffer Overflow and Congestion-Sudden as one congestion family. Published results are cited for context only (Section 5.5).

**Track B: explanation quality (G-Eval).** Rodina Khallaf's Track B applies an LLM-as-judge protocol based on G-Eval [@liu2023geval] to KPI-RAG explanations of 30 fault windows. Each explanation is scored against a structured ground-truth reference on citation validity, fault specificity, actionability and causal soundness, each on a 1 to 5 integer scale with a rubric calibrated against expert-written explanations; the composite is their unweighted mean. Track B is reported on its own and is not combined with the Track C counts.

**Track C: citation ablation.** Ahmed Al Shobaki's Track C runs the full system under C1, C2 and C3 on identical windows. The first prototype drew 3 test windows for each fault with a 3GPP reference (seed 42) and scored validity against the predicted fault's row. The later audit of the ablation runs found that sampling windows by predicted label mixed Normal and misclassified windows into the sample. The final design samples three windows per true fault type (seed 42) and counts a citation as correct only if it is valid for the true fault. A misclassified window that receives the wrong row, or a missed window, therefore counts as incorrect. Validity against the predicted row, the closest analogue of the first prototype's measure, is also recorded. Two rules that need no LLM are scored on the same windows: always citing the standard most often correct (TS 38.141-1 [@ts38141]) and citing the predicted fault's row. Wilson 95 % intervals [@wilson1927] and exact McNemar tests [@mcnemar1947] describe effect sizes and are not read as significance tests. The O4 target of at least 70 % correct citations is checked on the cited specification number, since clause numbers are not validated. A separate retrieval experiment compares four designs on the 266 detected test faults by precision@1 and @5, against the majority-class share and the classifier's label accuracy. The designs are tickets with and without the label in the query, KPI narratives, and narratives embedded by averaging all paragraphs.

**Track D: TeleQnA.** Rodina Khallaf's Track D characterises the knowledge scope of the retrieval pipeline on the TeleQnA multiple-choice benchmark [@maatouk2025teleqna], using the Standards specifications, Standards overview and Lexicon categories; the two research categories are excluded. The LLM answers with no context and with KPI-RAG, whose retriever queries a ChromaDB knowledge base of 935 fault-diagnosis telemetry tickets and prepends the top-k chunks. A coverage audit marks a question as supported when its top similarity reaches τ = 0.50, and a post-hoc confidence gate on the stored answers keeps the KPI-RAG answer only when the top similarity reaches τ (swept from 0.20 to 0.60). Track D therefore evaluates retrieval over this ticket corpus, not the deployed retrieval over per-window narratives.

### 3.12 Tools and resources

The ML layers use Python with scikit-learn [@pedregosa2011sklearn], CatBoost, LightGBM, XGBoost, aeon and SHAP, in numbered scripts with seeded randomness and pinned versions. The explanation layer uses Python 3.11 managed with uv, sentence-transformers, ChromaDB 1.5 (HNSW search [@malkov2020hnsw]), the google-genai, groq and openai clients, pydantic, Streamlit 1.61 [@streamlit] and pytest, with its parameters in `configs/config.yaml`. CatBoost and SHAP need no graphics processing unit (GPU). LLM development for the first prototype used the Queen's University high-performance computing (HPC) cluster (Frontenac); the final evaluation and the public demonstration on Streamlit Community Cloud call Gemini on a free-tier quota. The data resources are TelecomTS (MIT licence), the GSMA telecom-kg-rel19 and O-RAN specification knowledge graphs (CC BY-NC 4.0), TeleQnA and the 3GPP Release 19 specifications.

Chapter 4 describes how these methods are implemented in the final system.

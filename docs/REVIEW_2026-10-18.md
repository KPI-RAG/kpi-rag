## 2. Findings in detail

### 2.1 — Track C mixes two Layer 2 models and injects foreign RCA evidence (P1)

`scripts/run_eval_track_c.py:82-113` (commit `afa7f8a`) and `:166-174`.

The Phase 2 model predicts only 3 congestion windows (Gradual 2, Sudden 1) among its 382
fault predictions. To reach 3 per fault, the script backfills from
`layer2_rag_handoff_sessionsplit.json` — the **Phase 1** model's predictions, SHAP and
confidence. The three backfilled windows:

| window | Track C label (Phase 1 pred) | ground truth | Phase 2 pred |
|---|---|---|---|
| 829 | Congestion (Gradual) | Antenna Failure | Buffer Overflow |
| 608 | Congestion (Sudden) | CCI Severe | CCI Severe |
| 624 | Congestion (Sudden) | CCI Severe | Faulty RF Filters |

None is congestion by truth or by the current model. Because each one's own RCA record has a
different `predicted_fault`, line 172 falls back to `find_by_fault()` and injects a
**different window's** evidence, headed `[RCA PIPELINE EVIDENCE — window <other>]` and
including that record's `Standards grounding: TS …` line.

```
C3 total 30   own RCA 27   substituted 3   (829, 608, 624)
```

So the README's "RCA evidence was injected for 30/30 C3 samples" counts 3 substitutes. The
warning at line 144 ("…window_index >= 1235 … will carry no RCA evidence") is now false on
both counts: RCA v2 holds 289 records (max index 31997), and the fallback does inject.

**Fix.** Sample from one prediction source only. Report congestion with n < 3, or adopt the
ground-truth stratification from prior 1.2. Never inject a representative record into a
prompt; if the window has no matching record, send none and count it.

### 2.2 — Sampling by prediction (prior 1.2, still open) (P1)

Against the handoff ground truth:

```
Track C samples that are anomalous windows : 22 / 30   (8 are normal windows flagged as faults)
predicted == ground truth                  : 13 / 30
```

17/30 (57 %) of samples are false alarms or the wrong fault. All 30 now have *some* RCA
record (27 own, 3 substituted — see 2.1), so the "C3 without RCA" symptom from the last
review is gone, but the design issue remains: Track C measures *grounding given a
prediction*. Either say exactly that in the report (with the 13/22 accuracy and 8 false
alarms) or resample by true label.

### 2.3 — Ablation confound in the prompts (P1)

`src/llm_explainer.py:128-137`. Only the C3 prompt contains:

- "Use TR (Technical Report) instead of TS when the standard is a TR -- for example, channel models use TR 38.901."
- "Ground your explanation in the specific KPI values and SHAP evidence provided above."
- different per-field descriptions in the JSON schema (e.g. `"TS/TR XX.XXX (e.g., TS 38.321 or TR 38.901)"`).

The C2→C3 delta (+77 pp) therefore measures *context + instructions*, not context alone.
Use one shared instruction/schema block across C1–C3, or state the confound.

### 2.4 — LLM failures are swallowed (P1)

`src/llm_explainer.py:365-371`. Any exception that is not a rate limit — missing API key,
auth error, malformed JSON — is caught with no log line and the call is retried
immediately. Reproduced with `GEMINI_API_KEY=` unset:

```
ERROR src.llm_explainer: All 3 LLM attempts failed, using template fallback
template True secs 4.0
```

The cause never appears; three calls are spent on a non-retryable error. The dashboard then
captions it "Generated from alignment table template (LLM parse failed)"
(`dashboard/components/explanation_panel.py:31`), which may be the wrong reason.

**Fix.** `logger.warning("Attempt %d failed: %r", attempt, e)` on every failure; break out
immediately on configuration/auth errors (`ValueError`, `RuntimeError`, 401/403).

### 2.5 — `src/ml_model.py` is not part of any pipeline (P1)

- Only `tests/test_phase2_models.py` imports it. `run_pipeline.py`, `dashboard/app.py` and
  `run_eval_track_c.py` all consume precomputed JSON.
- No code in the repo turns a raw window into the 64 / 496 features, so the models cannot
  be run end to end and `validation.json`'s reproducibility claim cannot be re-run here.
- Both `.cbm` files carry anonymous feature names (`m1.feature_names_[:3] == ['0','1','2']`),
  so column order cannot be verified against `feature_spec.json`; tests check counts only.
- Class mapping is correct: model1 `classes_ = [0, 1]` (so `proba[1]` = P(anomalous));
  model2 argmax maps to its 11 named classes.
- Smaller: unused `os` / `pickle` imports; `calibrator_path` read but never used;
  `predict()` calls `predict_proba` twice; the returned confidence is model1's P(anomalous)
  even when a fault class is returned — a different meaning from the `confidence` field in
  the Phase 2 JSON.

**Fix.** Either add a tested `build_features(window) → predict()` path and call it from the
pipeline/dashboard, or document Layer 2 as precomputed offline and mark `ml_model.py`
accordingly. If the calibrator is abandoned, delete `model1_calibrator.pkl` rather than ship
a pickle.

### 2.6 — Dashboard runs on Phase 1 data (P1)

`dashboard/app.py:104` loads the Phase 1 handoff file; RCA evidence (`:93`, `:189`) is
Phase 2.

```
handoff windows in train split                 : 935 / 1235
handoff windows with an RCA v2 record          : 173
  … of which RCA predicted_fault != handoff label : 45
own ticket in top-5 (40 sampled train windows) : 2 / 40
```

For those 45 windows the prompt says "Fault detected: X" while the injected RCA block says
"Predicted fault: Y" — Track C guards against this (line 169), the dashboard does not. The
comment at `app.py:247` ("only covers the 1,235 anomalous windows") is stale.

**Fix.** Load `layer2_output_sessionsplit_phase2.json`, restricted to `test_idx`, and apply
the same `predicted_fault == label` check before injecting RCA context.

### 2.8 — Alignment table source of truth (P2)

`run_eval_track_c.py:41`, `run_pipeline.py:21`, `app.py:86`). The copies are currently
identical. Keep one file and read the path from config.

Prior 1.13 is still open: 9/10 rows `validation_status: "pending"`, `validated_by` empty,
while the header text claims pending validations are cleared.
